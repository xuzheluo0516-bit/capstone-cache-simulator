# 自定义策略设计文档：RW-CSF

> 对应 Issue #10（设计文档、可运行实现、测试、局限说明）。
> 实现：`src/cache_simulator/rwcsf.py`，CLI 名称 `CUSTOM`；测试：`tests/test_rwcsf.py`。
> 对比基线：`src/cache_simulator/gdsf.py`（CLI 名称 `GDSF`），测试：`tests/test_gdsf.py`。

## 1. 优化目标

**主目标：平均响应时间**（课程模型：命中 5 ms，未命中 = 源站延迟）。

同时报告：请求命中率、字节命中率、源站流量、每客户端结果。
RW-CSF 不要求在所有指标和所有负载上胜出；目的是说明它在哪些条件下更好、代价是什么。

动机（共享缓存里资源的价值并不相同）：

- FIFO、LRU 不看资源大小与源站延迟。
- LFU 的累计次数永不衰减，过去的热门资源会长期占着缓存。
- 一个大文件可能一次挤走多个"小而慢"的热门页面。

RW-CSF 的想法：把缓存空间当作有限资本，优先保留"当前每占一字节空间、能省最多时间"的资源。

## 2. 策略定义

对缓存中的资源 $i$，在第 $n$ 个请求时：

$$P_i(n)=\frac{F_i(n)\cdot \Delta T_i}{s_i},\qquad
F_i(n)=\sum_{j\in A_i}2^{-(n-n_j)/H},\qquad
\Delta T_i=\max(\ell_i-h,\,0)$$

- $F_i$：近期加权访问次数。每次访问计 1 分，每过 $H$ 个请求权重减半。
- $\ell_i$：该资源的源站延迟；$h$：命中延迟（课程固定 5 ms）。
- $\Delta T_i$：命中一次真正省下的时间。
- $s_i$：资源大小（字节）。
- **淘汰 $P$ 最小者。** 平局时淘汰最近最少访问者，再平局按 `ResourceKey` 排序（保证确定性）。
- 零字节资源 $P=\infty$（淘汰它不释放空间，所以只有缓存里没有别的资源时才会被选中）。

$H$ 的单位是**请求数**，不是时间。

### 增量更新（实现方式）

- 插入：$F\leftarrow 1$，记录 $n_{last}\leftarrow n$。
- 命中：$F\leftarrow F\cdot 2^{-(n-n_{last})/H}+1$，$n_{last}\leftarrow n$。
- 淘汰：该资源的记录删除（与课程 LFU 一致，淘汰后历史清零）。

## 3. 数据结构

每个缓存中的资源一条记录：

| 字段 | 含义 |
|---|---|
| `F` | 上次访问时的衰减频率 |
| `last`（$n_{last}$） | 上次访问的请求序号（同时用作"最近最少访问"平局依据） |
| `(ΔT, s)` | 由 `should_admit(resource)` 读入的收益与大小 |

引擎只把 key 和 step 传给多数回调，资源大小和延迟是在 `should_admit` 中记录的（该函数**始终返回 True**）。
也可以在构造函数中传入 `resources=`。

可选参数（实验用）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `half_life` | 20.0 | 半衰期 $H$（请求数）；`math.inf` 表示不衰减 |
| `hit_latency_ms` | 5.0 | 与引擎一致 |
| `use_latency` | True | False 时 $\Delta T$ 取 1（消融用） |
| `use_size` | True | False 时 $s$ 取 1（消融用） |
| `inherit` | False | True 时淘汰的资源进入"遗忘表"，再来时先衰减再加 1 |
| `forget_limit` | 1000 | 遗忘表上限 |

## 4. 伪代码

```text
on should_admit(resource, n):
    info[resource.key] = (max(resource.origin_latency - h, 0), resource.size)
    return True                      # 不做准入拒绝

on insert(key, n):
    F[key] = 1;  last[key] = n

on hit(key, n):
    F[key] = F[key] * 2**(-(n - last[key]) / H) + 1
    last[key] = n

select_victim(resident_keys, n):
    for key in resident_keys:
        P[key] = F[key] * 2**(-(n - last[key]) / H) * dT[key] / size[key]
    return argmin over key of (P[key], last[key], key)

on evict(key, n):
    delete F[key], last[key]
```

## 5. 手算验证例子

设置：容量 100 KiB，命中延迟 5 ms，$H=10$，每个资源 30 KiB。
A、C、D 源站延迟 105 ms（$\Delta T=100$），B 源站延迟 35 ms（$\Delta T=30$）。
请求序列 A, A, A, B, B, C, D；第 7 步请求 D 时缓存里有 A、B、C，必须淘汰一个。

| 资源 | LRU 依据 | LFU 依据 | RW-CSF（$n=7$） |
|---|---|---|---|
| A | 最后访问第 3 步（最久） | 频率 3 | $F=2^{-0.6}+2^{-0.5}+2^{-0.4}\approx2.12$，$P\approx7.08$ |
| B | 最后访问第 5 步 | 频率 2 | $F=2^{-0.3}+2^{-0.2}\approx1.68$，$P\approx1.68$ |
| C | 最后访问第 6 步 | 频率 1 | $F=2^{-0.1}\approx0.93$，$P\approx3.11$ |
| 被淘汰 | A | C | **B** |

三个策略淘汰的资源各不相同。RW-CSF 淘汰 B，是因为它命中一次只省 30 ms，却占着和别人一样的空间。
该例子已写成单元测试（`tests/test_rwcsf.py`）。

## 6. 与三种标准策略的本质区别

| 策略 | 依据 | 看不到的信息 |
|---|---|---|
| FIFO | 进入缓存的先后 | 访问、大小、延迟 |
| LRU | 最近一次访问 | 访问次数、大小、延迟 |
| LFU | 累计访问次数（淘汰后重置） | 近期性、大小、延迟 |
| **RW-CSF** | 衰减频率 × 命中收益 ÷ 大小 | `client_id`、真实时间（只用请求序号）；用到了近期性、频率、大小、延迟四类信息 |

与 GDSF 的区别：GDSF 用累计频率，并用膨胀值 $L$ 实现老化；RW-CSF 不用 $L$，而用指数衰减让旧热点自然褪色。两者使用同一个命中收益 $\Delta T=\max(\ell-h,0)$ 和同一个大小 $s$，所以对比的差别只在"频率怎么累计、老化怎么做"。
RW-CSF 可以概括为"把 LRFU 的衰减频率扩展到大小和延迟各不相同的 Web 资源，并用 $\Delta T/s$ 作为权重"。
这个思路不是首创（参考 GreedyDual-Size/GDSF 和 LRFU），组合与论证是本项目自己的。

自检性质（已有测试覆盖）：令 $\Delta T=1,\ s=1,\ H\to\infty$，RW-CSF 与 LFU 的淘汰顺序一致；令 $\Delta T=1,\ s=1,\ H=1$，与 LRU 一致。

## 7. 优点、缺点与适用条件

以下"可能更好/更差"是设计时的预期，是否成立以实验结果为准，不预先当作结论。

**可能更好的情形**

- 混合负载中有大文件消费者：大文件的 $\Delta T/s$ 低，被挤出的速度快，小而慢的热门页面能留得更久。
- 热点漂移的负载：旧热点自然衰减，不会像 LFU 被历史次数卡住。
- 资源大小和延迟差异大的负载：LRU、LFU 看不到这些信息。

**可能更差的情形**

- 所有资源大小与延迟接近、重复规律稳定：优势消失，表现接近 LRU/LFU 的折中。
- 字节命中率：策略偏爱小而慢的资源，字节命中率可能不如 LFU。
- 大文件消费者个体：整体平均响应时间变好，但这类客户端可能变差——这是取舍的直接体现。
- $H$ 敏感：选得不合适可能退化。（在本项目合成负载的四档 $H$ 范围内没有观察到明显敏感，见 §9，但不排除其他负载。）

## 8. 局限

1. **大文件插入当下仍会挤走别人。** 本策略只能让它下一轮先被淘汰，挡不住这一次。要挡住必须做准入拒绝。
2. **不做准入拒绝。** `should_admit` 恒为 True。课程说明对"策略能否拒绝准入"有歧义，需先向助教确认；`interface_v1.md` 也规定确认前不得拒绝。`admission` 开关在代码中**没有实现**，只作讨论。
3. **公平性不放进策略。** 接口回调拿不到 `client_id`。公平性只在分析阶段评价（每客户端命中率与平均响应时间、最差客户端响应时间、Jain 指数）。
4. **$H$ 在合成负载上选定。** 真实流量可能不同；报告里要明确这一点。
5. **没有真实 trace。** 所有结论都来自合成负载。
6. **策略评分依赖固定的 5 ms 命中延迟。** `hit_latency_ms` 默认 5.0，需与引擎一致。命令行 `python -m cache_simulator --hit-latency X` 只改引擎，**不会**传给策略（策略按默认 5.0 构造），所以课程要求的 5 ms 下没有问题，改该参数时需同步修改策略参数。

## 9. $H$ 的选取与记录

**预先固定的规则（先写下来再跑）：** $H\in\{5,20,100,500\}$；在调参 trace（种子 31415，与正式实验种子 20261111–20261115 不同）上，三种负载、五档容量都跑；对每种负载先对容量取平均响应时间，再对三种负载取平均；选最小者，平局取较小的 $H$。选定后固定，不按负载单独调整。

**调参结果（种子 31415，large）：**

| $H$ | 平均响应时间（ms） |
|---|---|
| 5 | 88.3518 |
| 20 | 87.9753 |
| 100 | 88.2438 |
| 500 | 88.2106 |

按规则选定 $H=20$。四个取值之间的差距只有约 0.4%，说明在这四档范围内 RW-CSF 对 $H$ 不敏感，选择 20 依据的是微小差距，不应解读为"20 显著最优"。

复现命令：

```text
python d_experiments/run_h_tuning.py --output-dir data/experiments/h-dry-run
```

**参数可追溯：** 批量实验把 $H$ 写进每次运行的 `manifest.json` 的 `policy_parameters.CUSTOM.half_life`，因此每个结果都能反查它用的 $H$。批量实验命令 `python -m cache_simulator.experiments` 可以用 `--policy-parameters-json` 传入。`rwcsf.py` 里的默认值 `DEFAULT_HALF_LIFE = 20.0` 与选定值一致。

注意：只有 15 个请求的参考 trace 上，$H\ge 20$ 基本等于不衰减；而调参和正式实验用的 trace 有 1440 个请求，$H=20$ 是真实起作用的衰减。
